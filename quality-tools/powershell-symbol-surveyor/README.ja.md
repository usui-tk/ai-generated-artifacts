# PowerShell Symbol Surveyor

> 🇺🇸 [English](./README.md) / 🇯🇵 日本語

ここには 2 つのツールがあります。

| ファイル | 役割 |
|:--|:--|
| `pss.py` | サーベイヤ本体。1 つの PowerShell スクリプトからシンボルモデルを抽出します。契約: [`SPEC.md`](./SPEC.md)。 |
| `test_pss.py` | ベースラインゲート (§13.1)、およびゲートがサーベイヤを動かすために使う 2 つの装置 — **コーパス管理** (`test_pss.py corpus <subcommand>`, §14.2) と**派生キャッシュ生成器** (`test_pss.py cache <entry>`, §14.4)。 |

`SPEC.md` が `pss.py` と §14.4 のキャッシュ契約についての正本です。
本 README がコーパス管理についての正本で、コーパスのガバナンス規則は
[ADR 0033](../../governance/adr/0033-pss-test-corpus-governance.md) に durable な形で置かれています。

---

## なぜコーパスが必要か

サーベイヤの要件は、「何が必要か」を尋ねて決めたものではなく、**実測された被害**から導かれています。
誰にも気づかれなかった失敗は、それを見逃した当人には報告できないからです。
そのように要件を導くには実材料が要り、このリポジトリ自身の git 履歴がまさにそれにあたります —
所有者が管理しており、コミット済みの世代は決して変化しません。

コーパスの「エントリ」がその材料の単位です: 1 つのスクリプト、1 つのパス、連続した 1 つの世代の並び。

---

## エントリを形づくる 2 つの規則

**1. エントリはリネームを追わない。** `git log --follow` は記録された事実ではなくヒューリスティックであり、
`git show <rev>:<現在のパス>` は移動前のすべての世代に対して**静かに失敗**します。
1 つのパスに固定することで、この 2 つの失敗モードを防御的コーディングではなく**構造として**取り除きます。
エントリが記録するすべての世代は、そのパスにブロブが存在することが証明された世代です。
スクリプトが移動したら、古いエントリは封鎖され、新しいエントリが登録されます。

**2. エントリは追記のみ。** `update` は世代リストを再導出し、既存の記録が新しい記録の
厳密な前方一致でない場合は**拒否**します。書き換えられた履歴は吸収されず、新しいエントリの登録を促されます。

---

## エントリファイル

エントリは `corpus/NNNN-<説明的な名前>.json` に置かれます。**識別子は先頭 4 桁のみ**で、
それ以降の説明部分は読み戻されません。5 桁目は拒否され（`00012` が `0001` + `2` と誤読されるのを防ぐため）、
番号の重複も拒否されます。

ヘッダの `start_rev` / `end_rev` / `count` は記録から導出できる値の再掲ですが、
これは意図的な冗長性であり、読み込み時に**検証されます**（信頼されません）。

形式はリポジトリ内の先例
`projects/bash-ol-aws-ami-builder/tests/ena/ena-driver-releases.json` に倣い、
メタデータのヘッダ 1 行のあとに 1 行 1 レコードを並べます。
これにより世代の追加が 1 行の diff になります。

```json
{
  "schema_version": "1.0",
  "list_type": "pss-corpus-entry",
  "generated_by": "quality-tools/powershell-symbol-surveyor/corpus.py",
  "repo": "ai-generated-artifacts",
  "script_path": "projects/powershell-update-windows-server-iso/Update-WindowsServerIso.ps1",
  "start_rev": "7566d22cf5f09a74523418a23a7c5001502c8633",
  "end_rev": "aade522845fa351cf4bb0f7f81fe72d79eb9bee4",
  "count": 157,
  "generations": [
    { "rev": "...", "date": "2026-06-08", "blob": "...", "subject": "..." }
  ]
}
```

`blob` はその世代におけるスクリプトの内容ハッシュです。`rev` とは独立した整合性チェックであり、
履歴が書き換えられるとコミットハッシュは必ず変わる一方、ブロブハッシュは内容が変わった場合にのみ変わります。
両方を保持することで、**書き換えられた履歴**と**改変された内容**を区別できます。

### ツールが書き、人は書かない

エントリはコーパス管理を通じてのみ書かれます。これはマニフェストが `canon-manifest-tool` を
通じてのみ書かれるのと同じ考え方です (ADR 0011)。`generated_by` フィールドがその書き手を記録します。

> **注記 (2026-08-18)**: `generated_by` の値は `.../corpus.py` のままです。
> 管理機能は `test_pss.py` のサブコマンドに移りましたが、エントリは構造としてバイト安定であり —
> そのバイト安定性こそが成長検知を可能にしています — 文字列を貼り替えると、
> エントリについての事実ではなくツールについての事実を記録するために、
> コミット済みの成果物 2 件を書き換えることになるためです。

### タイムスタンプを持たない

書かれたエントリにタイムスタンプは含まれません。成長の検知が「再生成して比較する」ことである以上、
バイト安定性がその前提だからです。

### 封鎖状態は導出される

エントリは自分が封鎖されたかどうかを宣言しません。HEAD にパスが存在するかどうかから導出されます。
保存された状態は、それが記述する対象と食い違いうる 2 つ目の写しになります。

## 使い方

```
# エントリを登録する（.ps1 を 1 つ。ディレクトリと glob は拒否される）
python3 test_pss.py corpus --repo <repo> add <path/to/Script.ps1> [--slug <text>]

# 導出ビュー: 識別子・封鎖状態・範囲・無視されたファイル
python3 test_pss.py corpus --repo <repo> list

# 全エントリを現在の git と照合する。findings のみで、何も適用しない
python3 test_pss.py corpus --repo <repo> check

# 新たにコミットされた世代を 1 つのエントリに追記する
python3 test_pss.py corpus --repo <repo> update <NNNN>
```

`check` は成長と書き換えを findings として報告し、再固定は一切行いません。
再固定は意図的な `update` であり、ADR 0011 / ADR 0027 の
「機械が提案し、人が決める」分担に沿って通常のパッチフローを通る、裁定された変更です。

`check` は**常設のゲートバッテリーには含まれません**。監視対象のスクリプトは保守ストリームの
所有物で保守側の速度で進むため、ガバナンスのバッテリーに組み込むと、
通常のプロジェクト作業がガバナンスストリームの赤になってしまいます。
コーパスそのものが主題であるときに実行してください。

### 分析

エントリの世代に対して 3 つの reduction が動きます。いずれも**カウントと観測を報告するだけで、
判定は出しません** — サーベイヤ本体の契約 (`SPEC.md` §1.2) と同じです。

```
# 世代ごとの関数削除と、モデルがまだそれを参照していたかどうか
python3 test_pss.py corpus --repo <repo> deletions <NNNN>

# 指名した関数の呼び出し元数の推移
python3 test_pss.py corpus --repo <repo> transitions <NNNN> --targets Get-Foo Set-Bar

# これまでに定義されたことのある名前と、最終世代に存在する名前の対比
python3 test_pss.py corpus --repo <repo> ever-defined <NNNN>
```

大きなスクリプトの全世代を調査するには数分かかります。`--limit N` で直近 N 世代に絞れます。
分析はファイルを書きません — ADR 0028 のホット/コールド観測の分離と同じ考え方で、
出力は意図的に transient です。

解決しなくなった pin はエラーになります。**決してスキップされません**:
エントリの記録は書かれた時点で解決することが証明されているので、
見つからないということはコーパスが壊れているということであり、それは表明されなければなりません。

## 派生モデルキャッシュ

エントリの全世代を調査するには数分かかるため、得られたモデルはリポジトリの外にキャッシュされ、
セッションをまたいで持ち運ばれます。`test_pss.py cache` が SPEC §14.4 の規定する生成器です。

```
# 1 エントリ、全世代、全軸
python3 test_pss.py cache 0002

# フル実行のコストを払わずに生成器を動かしてみる
python3 test_pss.py cache 0001 --limit 2 -o /tmp/sample.jsonl.gz
```

キャッシュは**派生データ**です: コミットされず、ベースラインにもならず、
どのビルドが生成したかが判明している間だけ使えます。
その最後の性質を担っているのがヘッダで、`pss_version` / `model_version` / `model_shape` /
`baseline_digest` と、どの世代にわたって何を調査したかを記録します。

出力を読む前に知っておく価値のある選択が 3 つあります。

**自分では identity を計算しない。** `baseline_digest` と `model_shape` は
`--emit-baseline-digest` が出力するのと同じ関数から取得され、コピーされます。
2 つ目の実装があると、キャッシュとそれを読むゲートが「何を測ったか」について食い違いえます —
ADR 0033 が退治した欠陥そのものです。生成器が独立したファイルだったころは
そのファイルに `hashlib` が存在しないことでこれを保証していましたが、
現在は生成器自身の関数を構文木で読むことで、同じ要件を統合後のファイルで可能な形で保証しています。

**世代は `rev` と `blob` であって、位置ではない。** identity はブロブにあります (ADR 0033)。
添字はファイル自身の並び順から導出できるので、保存すれば 1 つの事実に対する 2 つ目の出所が生まれ、
そして食い違いうるのは写しの側です。これは仮定の話ではありません:
散文に書かれた手順から作られた以前のキャッシュは、230 件すべてのレコードに
`gen_index: null` を持っていました。

**全軸が材質化され、それは選択肢ではない。** キャッシュは他のキャッシュと突き合わせてこそ有用で、
材質化の異なる 2 つのキャッシュは比較できません。軸集合を固定するのは高速でもあります —
すでに全軸を持つモデルは軸の増分を測定しないからです。

キャッシュは、モデルが何を出力するかが変わらない限り生き残ります。
現在のビルドと一致しない digest は、キャッシュが**別の**ビルドから来たことを示すだけで、
データが誤っているとは言いません。データがまだ比較可能かどうかに答えるのは `model_version` です。

## 2 つのモデルを比較する

`compare A B` は差異を述べ、入力間の関係については**いかなる主張もしません**。
`trace before after` は「2 つ目が 1 つ目の後の状態である」という**呼び出し側の主張**を伴います。
ツールにはその主張を検証できず、述べることを要求できるだけです。
だからこそフラグではなく動詞になっています。

```
python3 pss.py compare a.json b.json --format json
python3 pss.py trace before.json after.json --format json --out delta.json
python3 pss.py compare a.json b.json --all      # 主体ごとに等価性を明示する
```

出力は `delta_records`（差異のみ）、`surveyed`（コード別の集計）、
`examined_subjects`（比較母集団を識別子で列挙）を持ちます。3 つとも必要です:
`surveyed` に無いコードは**実行されていない**のであって、実行して何も見つからなかったのとは
異なります。`examined_subjects` に無い名前は比較されていないのであって、
変更が無かったのとは異なります。`compare` は継承の主張なしに成立する 15 コードを評価し、
`trace` はそれに加えて §12.7 の 3 規則を評価します。この 3 つは `trace` が運ぶ主張を前提とします。
いずれも**証拠つきの候補**を出すのであって、結論は出しません。

`model_version`・軸集合・スコープが一致しない場合は、部分的に比較せず**拒否します**。
部分的な差分は完全な差分として読まれてしまうためです。

## 自己テスト

```
python3 test_pss.py        # ゲート全体。コーパスの検査を含む
```

コーパスの検査は `test_pss.py` にサーベイヤ自身の検査と並んで置かれています。
SPEC §14.1 がこのツールを 2 つの `.py` ファイルに保つと規定しており、
コーパス用の 3 つ目はやはり 3 つ目だからです。**この規則はゲート化されました**:
ゲートがツールのファイル集合を列挙して完全一致を要求するため、
3 つ目のモジュールはステージ済みかどうかに関わらず失敗します。
この規則は 3 日間 normative でありながらゲートが無く、それがまさにファイル数が
5 まで増えた理由でした — ファイルを追加するには §14.1 とゲートのリストを
同時に編集する必要があります。
そのフィクスチャは一時ディレクトリに作られる**実際の git リポジトリ**です。
テスト対象の振る舞いが git の振る舞いそのもの — リネーム、削除、追記された履歴、
書き換えられた履歴 — だからで、モックは事実ではなく仮定を再現してしまいます。
そしてこのツールが対処しているトラップは、すべて仮定の失敗でした。
このチェックアウトではなく `git` バイナリを必要とするため、
バイナリが無い環境では**名指しで**スキップされます (§14.3)。

## 登録

`pss.py` もその装置もまだマニフェストに登録されていません。
`pss.py` は SPEC に provisional な項目が無くなった時点で登録され、装置はそれに随伴します。
奉仕する対象のツールより先にヘルパーを登録するのは順序が逆になります。

> **注記 (2026-08-18)**: 登録の先送りには、記録しておくべきコストが伴います。
> 導出されたバッテリーの対象リストはマニフェストを起点にしているため (ADR 0031)、
> 登録を先送りすると**このディレクトリに対する構造的なゲートもすべて先送りされます**。
> 実際、「2 つの `.py` ファイル」と書かれた仕様に反してファイル数が 3 日で 2 から 5 に増え、
> どのゲートもそれを見ることができませんでした — ベースラインゲートが読むのはモデルであって
> ディレクトリツリーではないためです。先に登録する案が提起されています。
