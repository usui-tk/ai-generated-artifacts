## 1. Step 4 系列のコードバグ修正経緯

実機検証を進める中で、Step 4a → 4b → 4c の 3 段階で**累積 5 個**のコードバグを修正した。各バグは Step 3 で導入されたコードに起因するものではなく、より深い層で長期間眠っていたものを Step 3 のフェーズ完成によって初めて顕在化させた。

### 1.1 Step 4a: install.wim の ReadOnly 属性によるマウント失敗

**症状:**
```
[X] Phase P07 (PatchInstallWim) failed:
    You do not have permissions to mount and modify this image.
    Verify that you have Read/Write permissions or mount the image
    using the /ReadOnly option.
```

**誤解しやすい点:** エラーメッセージは「permissions」と表示されるが、実態は Administrator 権限の不足ではない(P01 で `Running as Administrator` を確認済み)。

**根本原因:** P05 `Expand-SourceIso` が `robocopy /COPY:DAT` で ISO を展開する設計。`/COPY:DAT` の `A`(Attributes)が、**ISO ボリューム上のファイルが持つ ReadOnly 属性を、展開先にもそのままコピー**する。ISO ボリュームは設計上 read-only メディアなので、展開された `install.wim` は ReadOnly 属性付きになる。DISM の `Mount-WindowsImage` は対象 WIM が ReadOnly 属性を持つと書き込みモードでのマウントを拒否する(これは misleading なエラーメッセージで隠蔽されていた)。

**修正方針:** `Invoke-WimMountSafe` 関数(行 5963〜、すべての WIM マウントの共通入口)で、`Mount-WindowsImage` 呼び出し直前に対象 WIM の ReadOnly 属性を解除する処理を追加。

```powershell
# Mount-WindowsImage の直前に追加
Set-DebugStep -Step ('wim-mount-clear-readonly')
try {
    $wimItem = Get-Item -LiteralPath $ImagePath -Force -ErrorAction Stop
    if ($wimItem.IsReadOnly) {
        $wimItem.IsReadOnly = $false
        Write-Step ('Cleared ReadOnly attribute on WIM: {0}' -f $ImagePath)
    }
} catch {
    Write-Warn ('Could not inspect or clear ReadOnly attribute on {0}: {1}' `
                -f $ImagePath, $_.Exception.Message)
}
```

**修正の妥当性:**
- `Invoke-WimMountSafe` は install.wim / boot.wim / WinRE.wim すべての mount の共通入口 → 全 WIM に効く
- ReadOnly 属性が既に解除されているケースは no-op(無害)
- try/catch で best-effort、属性操作失敗時も後続の `Mount-WindowsImage` が本来のエラーを surface

**ScriptTag:** `add-output-iso-pca2023-verification` → `fix-readonly-attribute-on-wim-mount`

### 1.2 Step 4b: PatchType フィールド名不整合 + Transcript + Export の 3 バグ

Step 4a の修正で WIM マウントが成功するようになると、その先のフェーズで**新たに 3 つのバグ**が連鎖的に露呈した。

#### 1.2.1 バグ 1: Build-PatchPlan の `$_.Type` 参照(根本原因)

**症状:** P02 ログで `Install (2): ?/KB5087537, ?/KB5087065` と表示。`?` は PatchType が空または null。

**根本原因:** `ResolvedPatches` 構築箇所(行 9239)で:
```powershell
$resolved.Add([pscustomobject]@{
    ...
    KbId = $p.KbId
    PatchType = $p.Type   # ← フィールド名 PatchType
    ApplyOrder = $p.ApplyOrder
    ...
})
```
として、**わざと** `Type` ではなく `PatchType` という命名にしていた(PowerShell ETS で `.Type` という名前が特殊扱いされる可能性を避けるための設計判断)。

しかし、`Build-PatchPlan`(行 6954)では:
```powershell
$type = if ($p.PSObject.Properties['Type']) { [string]$p.Type } else { '' }
```
と書かれており、**`PatchType` ではなく `Type` を参照**していた。結果、ResolvedPatches を渡したときに常に空文字列となり、Plan.Install / Plan.Boot などへの target 分類が機能しなくなっていた。

`Write-PatchPlanSummary`(行 7181)も同じパターンで `$_.Type` を見ていた。

#### 1.2.2 バグ 2: P07 の `$firstPassPatches` null 化(派生問題)

`Build-InstallApplySequence` も同じ `Type` 参照バグを抱えていたため、サブフェーズへの patch 分類が機能せず、全サブフェーズが 0 patches 状態に。結果、P07 で:
```powershell
$firstPassPatches = @($installSequence | Where-Object {...} | ForEach-Object { $_.Patches }) | 
    Where-Object { $_ }
```
の結果が **null** になり(空配列ではなく)、`Test-PatchDependencyClosureOnMount -PatchesToApply $null` で Mandatory パラメータエラー発生。

#### 1.2.3 バグ 3: catch ブロック内 `Export-DebugTraceJson` の誤パラメータ

スクリプト末尾の catch ブロック(行 12672)で:
```powershell
Export-DebugTraceJson -OutputDir $Script:DiagDir | Out-Null
```
と書かれていたが、`Export-DebugTraceJson` の正しいパラメータは `-Path <file>`。`-OutputDir` というパラメータは存在しない。これは catch 内で try/catch に握り潰されていたが、Transcript に「終了エラー」として記録され、エラー解析を混乱させていた。

#### 1.2.4 バグ 4: Transcript の停止保証不足

`Start-Transcript` 後に `Register-EngineEvent PowerShell.Exiting` で `Stop-Transcript` を登録していたが、**PowerShell.Exiting イベントはホストプロセスが終了する時のみ発火**する。インタラクティブセッションでスクリプトを `.\script.ps1` のように実行した場合、スクリプト終了 → プロンプトに戻るだけでホストプロセスは終了せず、`Stop-Transcript` が呼ばれない → ユーザーが手動 `exit` するまで Transcript が止まらない問題があった。

**修正方針:**
- バグ 1: `Build-PatchPlan` と `Write-PatchPlanSummary` で `PatchType` 優先、`Type` フォールバックの dual-field 対応に変更。
- バグ 3: `Export-DebugTraceJson -Path <timestamped-file>` に修正。
- バグ 4: `$Script:TranscriptStarted` フラグ + `finally` ブロックで明示的 `Stop-Transcript` を呼ぶ。

**ScriptTag:** `fix-readonly-attribute-on-wim-mount` → `fix-patchtype-classification-and-transcript`

### 1.3 Step 4c: サブフェーズ分類関数群の同一バグ修正

Step 4b の検証で、P02 のターゲット分類(`Install (2): LCU/KB5087537, DotNet.Runtime/KB5087065`)は正しく動くようになったが、**InstallSequence の各サブフェーズが依然として 0 patches** という問題が判明。

**根本原因:** Step 4b では `Build-PatchPlan` と `Write-PatchPlanSummary` の 2 箇所しか修正していなかったが、**同じ `$p.Type` 参照バグが 4 関数(7 箇所目を含む)に残っていた**。

| 関数 | 行 | 用途 |
|---|---|---|
| `Build-InstallApplySequence` | 7040 | install.wim の I1〜I6 サブフェーズへの分類 |
| `Build-BootApplySequence` | 7123 | boot.wim の B1〜B4 サブフェーズへの分類 |
| `Build-WinReApplySequence` | 7158 | WinRE.wim の W1〜W4 サブフェーズへの分類 |
| `Invoke-PatchSubPhase` | 7396 | サブフェーズワーカーでのログ表示・CSV 出力 |

**修正方針(根本対応):** ロジック重複によるドリフトを根本的に防ぐため、**ヘルパー関数 `Get-PatchEntryType`** を導入:

```powershell
function Get-PatchEntryType {
    [CmdletBinding()]
    [OutputType([string])]
    param([Parameter(Mandatory)] [AllowNull()] $Patch)
    if (-not $Patch) { return '' }
    if ($Patch.PSObject.Properties['PatchType'] -and $Patch.PatchType) {
        return [string]$Patch.PatchType
    }
    if ($Patch.PSObject.Properties['Type'] -and $Patch.Type) {
        return [string]$Patch.Type
    }
    return ''
}
```

そして全 6 箇所(Build-PatchPlan、Write-PatchPlanSummary、Build-InstallApplySequence、Build-BootApplySequence、Build-WinReApplySequence、Invoke-PatchSubPhase)をこのヘルパーで統一。

**ScriptTag:** `fix-patchtype-classification-and-transcript` → `fix-subphase-patch-classification`

## 2. SSU 依存性問題の調査経緯

Step 4c の修正後、再実行でようやく `Add-WindowsPackage` が呼び出された。しかし新たに以下のエラーで失敗:

```
警告: パッケージ D:\UpdateWsi_2016\patches\Server2016\
       windows10.0-kb5087537-x64_*.msu を追加できませんでした
警告: Add-WindowsPackage に失敗しました。エラー コード = 0x800f0823
```

ここで重要な転換点が発生した。**ユーザーから「スクリプトの修正やワークアラウンド的な提案は一旦止め、調査優先で進めるべき」というご指摘**を受けたため、ローカルログの詳細解析と Microsoft 公式情報の調査に方針転換した。

### 2.1 addpkg.log の精査

`D:\UpdateWsi_2016\logs\addpkg_20260527-145733.log` を全行精査し、エラー前後の context を抽出。

#### 2.1.1 決定的なエラー行

```
2026-05-27 14:57:51, Error CBS 
  Package "Package_for_RollupFix~31bf3856ad364e35~amd64~~14393.9140.1.19" 
  requires Servicing Stack v10.0.14393.7692 
  but current Servicing Stack is v10.0.14393.693. 
  [HRESULT = 0x800f0823 - CBS_E_NEW_SERVICING_STACK_REQUIRED]
```

これは Windows servicing model の典型的な依存問題:

| 項目 | 値 |
|---|---|
| 適用しようとした LCU | `Package_for_RollupFix~...~14393.9140.1.19`(KB5087537) |
| LCU が要求する Servicing Stack バージョン | **v10.0.14393.7692 以上** |
| install.wim 上の現在の Servicing Stack | **v10.0.14393.693**(Server 2016 GA build 14393.0 の出荷時) |
| エラーコード | `0x800f0823 = CBS_E_NEW_SERVICING_STACK_REQUIRED` |

#### 2.1.2 MSU 内部構造の判定

addpkg.log の他の行から、KB5087537 の MSU 内部構造が判明:

| 項目 | 値 |
|---|---|
| MSU 内部の CAB | `Windows10.0-KB5087537-x64.CAB`(単一) |
| MSU 内部の manifest | `update.mum`(単一) |
| 内部パッケージ名 | `Package_for_RollupFix~31bf3856ad364e35~amd64~~14393.9140.1.19` |
| `update.ses` の存在 | **なし**(Combined LCU+SSU では存在することがある) |

`Package_for_RollupFix` プレフィックスと `update.ses` の不在は、**KB5087537 が standalone LCU(SSU を含まない)** であることを示唆。

#### 2.1.3 config-Server2016.json の誤記発見

`data/config-Server2016.json` の KB5087537 エントリに:
```json
"IsCombined": true,
```
と記録されていたが、addpkg.log の証拠から **これは事実と一致しない**(IsCombined であれば SSU を内包しており、`CBS_E_NEW_SERVICING_STACK_REQUIRED` は出ないはず)。

これは「手動で書かれた config の事実誤認」であり、Microsoft の権威ある依存性データ(`wsusscn2.cab`)と突合する仕組みがあれば未然に防げる類のミス。

調査の次のステップとして、Microsoft の公式情報源で KB5087537 の prerequisite を確認。

#### 2.2.1 公式確認の結果

複数のソースで以下が確定:

> **"The Servicing Stack Update corresponding to KB5087537 is KB5088064."**

(出典: techepages.com の KB5087537 解説ページ、Microsoft Update Catalog の KB5088064 ページ)

#### 2.2.3 install.wim の状況との照合

`Get-WindowsImage` の出力と Microsoft の公開仕様から:

| 項目 | 値 |
|---|---|
| Server 2016 GA install.wim の OS Build | 14393.0(2016 年 10 月リリース) |

つまり、Server 2016 GA EVAL ISO の install.wim に 2026-05 LCU を当てる正しい手順は:
1. KB5088064(SSU)を先に適用
2. その後 KB5087537(LCU)を適用

config に SSU エントリが存在しないため、ステップ 1 がスキップされ、ステップ 2 で CBS が拒否したのが今回の失敗の本質。

### 2.3 「コードバグ vs 構成問題」の判別

ここで重要なメタ判断: **今回の失敗はコードバグではなく構成問題**である。

| 観点 | Step 4a/4b/4c | Step 4d 候補 |
|---|---|---|
| 失敗の性質 | コードのフィールド名 / 属性扱い / catch ブロックのバグ | config に必要な KB エントリが欠落 |
| 対応 | スクリプト修正 | config 修正 |
| 防止策 | コードレビュー、テスト | **Microsoft 公式メタデータとの突合** |
| 推測修正サイクルでの解決可能性 | 可能(実際に解決) | **不可能**(構成の問題はコードで直せない) |

ユーザーのご指摘「推測ベースのスクリプト修正サイクルからの脱却」は、まさにこの「コードと構成の混同」を断ち切るためのメタ提案であった。これにより、暫定対応(config に SSU エントリを手動追加)で先に進めるか、根本対応(`wsusscn2.cab` を活用した自動検証機構の新設)に投資するか、の二択が浮上した。

### 3.2 議論の主要な意思決定の理由

#### 3.2.1 「1 GB のコストは投資として見合う」の判断

ユーザーからの提案「月次で 1 回だけのデータ処理であれば、1 GB のコストは投資として見合う」が、本設計の根本的な経済性を確立した。

定量的にも:
- 1 回の依存性エラーで失われる時間: 約 10 分 + 調査時間 30 分 = 40 分
- 実装コスト: エンジニア約 2-3 週間
- 月に 1 回のエラーで break-even: 約 6 ヶ月

今回 Step 4d の調査で既に数時間を消費しており、**1 回で実装コストの一部が回収できる**計算が現実的に証明された。

#### 3.2.2 「メンテナ手動コミット + ユーザー個別は cache だけ更新可能」(X-3)

ユーザーからのアイデア「メンテナだけが処理する。一度処理した結果をコミットすることで、各ユーザーは毎回処理しなくて済む」が決定的だった。

これにより:
- 世界中の利用者が個別に 1 GB ダウンロードする非効率を、メンテナ 1 人の月次作業に集約
- air-gapped 環境への対応も自然(committed layer 2 だけで動作可能)
- 各ユーザーは clone するだけで依存性検証が機能

#### 3.2.3 「Microsoft 由来テキストを除いた事実情報のみコミット」(X-1)

層 2 のファイル(`data/wsusscn2-database.json`)を Git にコミットする際の Microsoft ライセンス上の論点を整理。

| 含めるもの | 含めないもの |
|---|---|
| KB ID(事実) | KB タイトル(Microsoft の表現) |
| OS Build 番号(事実) | KB description |
| アーキテクチャ(事実) | 重要度等の人間可読プロセ |
| 関係性(prerequisite/supersedence、事実) | Microsoft 公式表現 |

この方針により、層 2 のサイズは想定 50-100 MB → **2-5 MB に大幅軽量化**され、Git 履歴肥大化対策も不要に。

本セッションで最も価値ある転換点は、**ユーザーからの方針提案**:

## 5. 教訓と再発防止

### 5.1 「コードバグ vs 構成問題」の判別を早期に行う

Step 4 系列の修正サイクルでは、初期段階で「コード変更で解決する性質か」「設定や外部要因で解決する性質か」を区別する習慣が不足していた。一般則:

| エラー特性 | 性質 |
|---|---|
| エラーメッセージがスクリプト内で生成されている | コードバグの可能性が高い |
| エラーメッセージが DISM / CBS / OS API 由来 | 構成問題の可能性が高い |
| 0x で始まる HRESULT エラー | Microsoft 公式エラーコードの可能性 → 検索優先 |
| ファイル属性、権限、サービス状態のエラー | 環境問題の可能性 → 環境確認優先 |

`0x800f0823 CBS_E_NEW_SERVICING_STACK_REQUIRED` は **明らかに 3 つ目** であり、コード修正サイクルに入る前に検索すべきエラーコードだった。

### 5.2 ヘルパー関数でロジック重複を排除する

Step 4b で `Build-PatchPlan` と `Write-PatchPlanSummary` の 2 箇所のみ修正したのは、症状ベースの最小修正だったが、**同じバグが 4 関数に残っていた**ことを Step 4c で発覚させた。

学び: 同じパターンのコードが複数箇所にあると、片方を修正してももう片方を見落とすリスクが高い。ヘルパー関数(`Get-PatchEntryType`)を導入して全箇所を統一する**根本対応** が、結果的に再発を防ぐ。

### 5.3 仕様優先のアプローチが議論の質を上げる

セッション中盤での「仕様検討を優先する」という方針転換は、その後の議論の質を劇的に改善した。設計判断の論点を列挙し、各論点に対する選択肢と推奨を整理する作業は、表面的な「コード修正」より遥かに価値の高い成果を生む。

学び: 複雑な問題に直面した際、「直す」よりも先に「**設計を考える**」フェーズを置くことで、再発を未然に防ぎ、似た問題の発生時にも対処可能な構造が手に入る。
