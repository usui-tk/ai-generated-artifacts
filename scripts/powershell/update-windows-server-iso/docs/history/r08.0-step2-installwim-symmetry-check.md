### 0.2 重要な発見・修正

**(1) Test-OutputIsoPca2023Readiness の必要性が明確化**

Build -Execute サマリで「作成された ISO が PCA2011 拒否環境で正常にブートできる」と claim するには、現状の P12 ロジック(入力 ISO 視点)だけでは不十分であることが、コード読解と Microsoft 公式仕様の照合により判明しました。Output ISO に対する post-build file-by-file 検証関数を追加する必要があり、次セッションのタスクとして明確に定義しました。

**(2) Microsoft 公式コードに署名検証ロジックは存在しない**

`Make2023BootableMedia.ps1` v1.4 は **ファイルコピーのみ** を行い、`Get-AuthenticodeSignature` / `signtool` の参照ゼロ。出力 ISO の検証は **呼び出し側の責任** という設計が確定しました。本リポジトリで `Test-OutputIsoPca2023Readiness` を追加するのは Microsoft 公式実装の **上位互換的品質改善** であり、設計と矛盾しません。

**(3) PowerShell `Get-AuthenticodeSignature` の解釈の落とし穴**

`Get-AuthenticodeSignature` は **leaf certificate の Issuer を直接返す** ため、Server 2025 `EFI_EX\bootmgfw_EX.efi` の場合「Issuer = Windows UEFI CA 2023」と表示されますが、chain build 結果としては `Root 2010 → Windows UEFI CA 2023 → Microsoft Windows (leaf)` という構造です。これは **PCA2023 単独署名** であり、dual-sign ではありません。本セッション中盤、これを「PCA2011 と思い込んで dual-sign を疑った」のは、Issuer フィールドの読み方を誤った私(Claude)側の認知バイアスでした。

## 1. 検査方法と検証スクリプト

### 1.1 step 5e/5f: install.wim 内部構造 + Authenticode 検査

**スクリプト**: `Invoke-InstallWimInspection.ps1`(本セッションで作成、`Get-AuthenticodeSignature` ベース)

**手順**:
1. ISO を `Mount-DiskImage` で読み取り専用マウント
2. `install.wim Index 4` を `dism /Mount-Wim ... /ReadOnly` で読み取り専用マウント
3. `\Windows\Boot\` 配下のサブディレクトリと file count を列挙
4. `\Windows\Boot\EFI\bootmgfw.efi` の Authenticode chain を `Get-AuthenticodeSignature` + `X509Chain.Build()` で取得
5. EFI_EX 存在時は `EFI_EX\bootmgfw_EX.efi` / `EFI_EX\bootmgr_EX.efi` の chain も取得
6. `finally` で DISM unmount + ISO dismount を必ず実行

**実行**: 4 OS (Server 2016/2019/2022/2025 EVAL ja-jp) 全てで実行。所要時間 1-2 分 / OS。

### 1.2 step 5g: signtool dual-signature 検査

**スクリプト**: `Invoke-Signtool-DualSignatureCheck.ps1`(本セッションで作成、当初 stderr エラーで catch block に流れる bug を経て修正)

**動機**: `Get-AuthenticodeSignature` は primary signature のみ返すため、もし dual-sign(`bootmgfw_EX.efi` が PCA2011 primary + PCA2023 secondary)であった場合に secondary signature を取りこぼす。それを確かめるため `signtool verify /pa /all /v` と `/ds 0`、`/ds 1`、`/ds 2`、`/ds 3` で全 embedded signature を明示的に enumerate。

**結果**: `EFI_EX\bootmgfw_EX.efi` も `EFI_EX\bootmgr_EX.efi` も **embedded signature 1 つだけ**。dual-sign ではないことが確証されました。

**バグ修正**: `$ErrorActionPreference = 'Stop'` のもとで signtool が `/ds 1` 試行時に "No signature found" を stderr に書いて exit 1 を返すと、PowerShell が terminating error として catch block に飛んでしまい、スクリプト全体が abort して `EFI_EX\*` の検査が一切実行されない bug が初回実行で発生。修正版では `Invoke-SigntoolSafe` 関数を新設し、signtool 呼び出しの前後だけ `$ErrorActionPreference = 'Continue'` に切り替え、出力を `[pscustomobject]@{ Output; ExitCode }` に集約する方式に変更。

### 1.3 step 5h: 4 OS 横断 `*.efi` 完全サーベイ

**スクリプト**: `Invoke-EfiSignatureSurvey.ps1`(本セッションで作成、データ駆動・事前仮説なし)

**動機**: step 5g で Server 2025 のみを対象とした検査では、Server 2016/2019/2022 install.wim 内の `*.efi` 群に PCA2023 が含まれる可能性が完全には否定できない。4 OS 横断で **事前仮説を一切持たず** に網羅サーベイし、データドリブンに「どの OS のどのファイルが PCA2023 化されているか」を集計。

**手順**:
1. 各 OS の install.wim Index 4 を読み取り専用マウント
2. `\Windows\Boot\` 配下の **全 `*.efi` を再帰列挙**
3. 各 `.efi` に対して `signtool verify /pa /all /v` 実行 → primary signature 数を集計
4. `/ds 0` / `/ds 1` / `/ds 2` で probe → PCA generation 別 count
5. CSV + summary JSON + 詳細 log の 3 ファイルを生成

**出力**:
- `<OsKey>_step5h_efi_survey.csv` — file × signature index の構造化データ
- `<OsKey>_step5h_efi_survey_summary.json` — 集計
- `<OsKey>_step5h_efi_survey.log` — signtool 詳細出力

## 4. 修正実装(Phase 1〜3 完了部分)

### 4.1 Phase 1: `Get-ConfigProfile` の dead code path 修正

**修正前の問題**: `Update-WindowsServerIso.ps1` L9740 / L9912 / L9975 で `$Script:OsProfile.EnableInstallWimUpdate` / `.EnableBootWimUpdate` / `.EnableWinREUpdate` を参照しているが、`Get-ConfigProfile` 関数(L2666 起点)が構築する merged object にこれら 3 フィールドが promote されていなかった。

**症状**: JSON の `Common.EnableInstallWimUpdate=true` を設定しても、`$Script:OsProfile.EnableInstallWimUpdate` は `$null` を返し、`if (-not $Script:OsProfile.EnableInstallWimUpdate)` は **常に true** に評価される。結果 P07/P08 が **dry-run でも -Execute でも常に skip** されていた。これは r07.0 cycle 通じて P07/P08 が dry-run で skip されていた根本原因。

**修正内容**: `Get-ConfigProfile` の `$merged = [pscustomobject]@{ ... }` ブロックに 3 つのフィールドを追加し、`$json.Common.<flag>` から promote。

```powershell
# Phase build-enable flags: promoted from Common so the build
# phases (P07 install.wim patching, P08 boot.wim patching) can
# access them as $Script:OsProfile.<flag> directly. Documented
# in SPEC.md B.4. These flags must be promoted explicitly here
# because PowerShell does not auto-flatten nested PSCustomObject
# properties; without promotion, callers reading the top-level
# property receive $null and the corresponding phase becomes
# unconditionally skipped regardless of profile content.
EnableInstallWimUpdate = $json.Common.EnableInstallWimUpdate
EnableBootWimUpdate    = $json.Common.EnableBootWimUpdate
EnableWinREUpdate      = $json.Common.EnableWinREUpdate
```
