## P0 — `Test-OutputIsoPca2023Readiness` function + P10/P12 integration (r08.0 Step 3, **HIGHEST PRIORITY**) — **CLOSED in r08.0 Step 3**

**Status**: closed 2026-05-27 by r08.0 Step 3 implementation.

**Resolution**: the function and its P10/P12/P13 integration shipped
in r08.0 Step 3. See
`docs/history/r08.0-step3-output-verification-and-build.md` for the
full implementation record:

- New function `Test-OutputIsoPca2023Readiness` (~290 lines) verifies
  the five Microsoft conversion targets defined in SPEC.md §B.18
  against the extracted output media. Returns a pscustomobject with
  per-target Status (Pass / PassWithNotes / Warning / Fail), an
  aggregate `OverallStatus`, and a `Reasons[]` array that always
  appends a SCOPE clarifier.
- `Get-Pca2023ReadinessSnapshot` carries the result on a new
  `OutputCheck` field; `Show-Pca2023ReadinessSnapshot` and
  `Format-Pca2023ReadinessForReport` render it via a new
  `-OutputCheck` parameter.
- P10 post-flight, P12 (always), and P13 FinalReport all surface the
  output-check status. JSON / Markdown reports include the per-target
  table.
- Root cause of the r08.0 Step 2 `Argument types do not match`
  exception: the `@()` array subexpression operator fails on
  `List[object]` of `pscustomobject` items under PowerShell 7.4.x;
  `.ToArray()` is the safe alternative (`List[string]` is unaffected).

### Original investigation plan (preserved for archaeology)

### Context

r08.0 Step 2 cross-checked the Microsoft official
`Make2023BootableMedia.ps1` v1.4 and documented the **five conversion
targets** in SPEC.md §B.18:

| # | Target on extracted media | Required? | Expected signer |
|:-:|---|:-:|---|
| 1 | `\efi\boot\bootx64.efi` (or `bootaa64.efi`) | required | PCA2023 |
| 2 | `\bootmgr.efi` (ISO root) | optional | **PCA2011 by Microsoft design** |
| 3 | `\efi\microsoft\boot\efisys_ex.bin` | required | n/a (binary) |
| 4 | `\efi\microsoft\boot\fonts\*.ttf` | required | n/a (fonts) |
| 5 | `\EFI\Microsoft\Boot\boot.stl` | optional | n/a (cert trust list) |

The existing `Get-IsoBootCertReadiness` is oriented around the INPUT
(pre-conversion) ISO state. There is no in-tree function that
verifies the OUTPUT (post-conversion) extracted media against these
five targets.

Microsoft's upstream script performs no signature verification of
its own (zero `Get-AuthenticodeSignature` / `signtool` references in
the 1141-line script); verification is by design left to the
caller. Adding `Test-OutputIsoPca2023Readiness` to this pipeline is
therefore an upstream-compatible quality extension.

### Goal

A new function `Test-OutputIsoPca2023Readiness` placed near
`Get-IsoBootCertReadiness` in `Update-WindowsServerIso.ps1`, with the
following interface:

```powershell
$check = Test-OutputIsoPca2023Readiness `
    -ExtractedMediaPath '<path to extracted media tree>'

# Returns a pscustomobject:
#   .Available     [bool]
#   .ErrorMessage  [string] (when Available=false)
#   .OverallStatus 'Pass' / 'PassWithNotes' / 'Warning' / 'Fail'
#   .TargetChecks  [array of pscustomobject], each with:
#     .Label, .Path, .ExpectedSignature, .ActualSignature,
#     .IsPca2023, .IsPca2011, .Status, .Notes
#   .Reasons       [array of string]
```

Plus:

- `Show-Pca2023ReadinessSnapshot -OutputCheck $check` extension for
  the rendering side.
- P10 post-flight (`Invoke-BuildPhase10_ConvertPca2023BootManager` end)
  calls it and renders compact summary.
- P12 (`Invoke-VerifyPhase12_VerifyPca2023Readiness`) calls it and
  integrates result into `pca2023_readiness.json` + Markdown report.
- P13 FinalReport summary section includes Output ISO check status.

Status mapping for the 5 targets:

| Target | Status when ... |
|---|---|
| #1 PCA2023 detected | `Pass` |
| #1 PCA2011 detected | `Fail` (operational failure) |
| #1 unreadable / missing | `Fail` |
| #2 PCA2011 detected | `PassWithNotes` (Microsoft-design, cite L876-L884) |
| #2 PCA2023 detected | `PassWithNotes` (acceptable but unusual) |
| #2 missing | `PassWithNotes` (Microsoft says "if present") |
| #3 present | `Pass` |
| #3 missing | `Fail` |
| #4 N fonts present | `Pass` |
| #4 missing or empty | `Warning` |
| #5 present | `Pass` |
| #5 missing | `PassWithNotes` (Microsoft's own L910-L911 says "Skipping" is acceptable) |

`OverallStatus` aggregation: any Fail → `Fail`; else any Warning →
`Warning`; else any PassWithNotes → `PassWithNotes`; else `Pass`.

`Reasons[]` always includes a SCOPE clarifier:
> "SCOPE: file presence + signer-chain only. Actual boot behaviour
> on firmware with PCA2011 revoked DBX is NOT verified here.
> Manual boot test on hardware or a Hyper-V Gen2 VM with PCA2023
> Secure Boot template is required before production deployment."

### Implementation notes (lessons from the r08.0 Step 2 attempt)

r08.0 Step 2 attempted this implementation but hit a `System.ArgumentException:
Argument types do not match` error in PowerShell's
`[pscustomobject]` construction that was not root-caused within the
session budget. The implementation was reverted; the dead code path
fix (`Get-ConfigProfile` 3-flag promote) was kept since it was
independently validated.

**Likely root cause** (to be verified in Step 3):

PowerShell's strict type inference on `[pscustomobject]@{...}` may
reject re-assignment of a property initialised as `@()` (`object[]`)
with a value of type `System.Collections.Generic.List[object]`. The
existing `Get-IsoBootCertReadiness` uses the same pattern without
issue, so something in `Test-OutputIsoPca2023Readiness`'s construction
differed in a subtle way.

**Recommended approach for Step 3**:

1. Follow the existing `Get-IsoBootCertReadiness` pattern verbatim:
   declare the result `[pscustomobject]@{...}` once at function entry
   with all fields, then mutate individual properties as needed.
   Avoid building a "fresh" pscustomobject at function exit.
2. Avoid inner function definitions (`function New-TargetCheck { ... }`
   inside the main function). PowerShell re-defines the inner
   function on every call and the type inference is fragile in this
   pattern.
3. If a helper is needed, hoist it to top level next to
   `Test-Pca2023AuthenticodeChain` (similar style to that helper).
4. Use `[pscustomobject]@{...}` inline at each TargetCheck site rather
   than a helper-returning-pscustomobject.
5. Lists: use a typed `System.Collections.Generic.List[object]` and
   convert to array at the end via `@($list)` for assignment.
6. Test on Linux pwsh 7.4.6 (the development environment used in
   Step 2) before declaring done, since strict type inference
   differs slightly between Windows PowerShell 5.1 and PowerShell 7.x.

### Investigation plan

1. Re-read the Step 2 implementation attempt logged in the finding
   doc §5.1 to understand what was attempted and why it failed.
2. Implement following the `Get-IsoBootCertReadiness` template
   (which is known to work).
3. Local test: synthesise a fake extracted media tree under

   - empty tree (all targets missing) → expect `Fail` on UEFI critical

   - bootx64.efi PCA2023 + bootmgr.efi PCA2011 → expect `PassWithNotes`
4. Run quality gates: psa.py (target 0/0/0), psa.py v4.1.0,
   PSScriptAnalyzer (target 0 findings), T2/T3/T6 (no regression).
5. Wire into P10 post-flight and P12.
6. Update SPEC.md §B.24.6 to move `Test-OutputIsoPca2023Readiness`
   from "new open items" to "closed in Step 3".

## P1 — Server 2025 EFI_EX directory: actual signature of bootmgfw_ex.efi — **CLOSED in r08.0 Step 2**

### Context

r08.0 Step 1 confirmed that Server 2025 EVAL install.wim ships
`\Windows\Boot\EFI_EX\` with 72 files, and confirmed that the

### Status (r08.0 Step 2)

✅ **CLOSED**: r08.0 Step 2 step 5g/5h directly inspected
`EFI_EX\bootmgfw_EX.efi` and `EFI_EX\bootmgr_EX.efi`. Findings:

- `EFI_EX\bootmgfw_EX.efi`: **PCA2023 single-sign**, chain root
  "Windows UEFI CA 2023", leaf signer "Microsoft Windows".
- `EFI_EX\bootmgr_EX.efi`: **PCA2011 single-sign**. This was
  initially surprising but confirmed as Microsoft-design behaviour
  by direct quote from `Make2023BootableMedia.ps1` v1.4 L876-L884:
  > "Note that this file technically is not signed with the
  > 'Windows UEFI CA 2023' certificate, but if present in the
  > update, it should be copied."

Neither file is dual-signed; `signtool /verify /pa /all /v` plus
`/ds 0`, `/ds 1`, `/ds 2`, `/ds 3` probes confirmed exactly one
embedded signature per file.

Evidence: `docs/history/r08.0-step2-installwim-symmetry-check.md`
§2.1 (4-OS table) + §3.2 (Microsoft official L876-L884 quote).

deployable output.

### Goal

Determine the **correct** workflow for producing a PCA2023-capable
Server 2016 ISO suitable for physical-hardware deployment, and
update the pipeline + documentation to support that workflow end
to end. The deliverable is one of:

- **Option A** — A profile change that enables
  `EnableInstallWimUpdate=true` for Server 2016, plus the
  patch-baseline updates (one or more LCUs leading up to 2024-4B
  or later) needed to lift the install.wim above the prereq, plus
  a verified end-to-end `-Execute All` run that produces an output
  ISO with `Health = Healthy` per P12.
- **Option B** — A documented workflow that uses a more recent
  Server 2016 ISO (e.g. a customer-supplied retail or volume-license
  media that already integrates a recent LCU) as the source, with
  the EVAL ISO documented as not viable for the PCA2023 use case.
- **Option C** — A documented finding that PCA2023 conversion is
  **not technically possible** on Server 2016 regardless of LCU
  level (e.g. because Server 2016 servicing is past the 2024-4B
  point at which Microsoft ships the EFI_EX staging assets), with
  evidence that closes the question.

### Investigation plan

**Phase 1 — Microsoft authoritative source**. Read the official
documentation for the
`Make2023BootableMedia.ps1` script and the
[microsoft/secureboot_objects](https://github.com/microsoft/secureboot_objects)
repository (the v1.4 / 2026-03-13 source the in-tree
`Convert-WimBootToPca2023Signed` was modelled after). Specifically:

1. What is the minimum supported source-media level for Server 2016?
2. Does the 2024-4B prerequisite apply to Server 2016 at all, or
   is it Windows 11 / Server 2022+ specific?
3. Does the EFI_EX staging directory ship with Server 2016 LCUs at
   any servicing date? Server 2016 is in Extended Security Updates
   (ESU) territory; ESU coverage and PCA2023 servicing may not
   overlap.

The likely answer is: **Server 2016 is not covered by the PCA2023
boot-manager refresh programme**. Server 2016 reaches end of
extended support on 2027-01-12 and is currently in ESU. The 2023
certificate refresh shipped via Windows 11 22H2/23H2 and Windows
Server 2025 servicing branches; backporting to Server 2016 was not
announced. If that is confirmed, the conclusion is Option C and the
pipeline needs to either (a) refuse `-EnablePca2023BootManager` for
Server 2016 with a clear error message, or (b) document the
limitation prominently in README so the operator does not waste
time on it.

**Phase 2 — Empirical check on Server 2016 LCU vintage**. If
Phase 1 leaves the question open:

1. Identify the most recent Server 2016 LCU available via Microsoft
   Update Catalog. As of 2026-05 this should be the 2026-05B LCU
   (the cycle the script currently targets).
2. Mount a fresh Server 2016 EVAL `install.wim` and apply that LCU
   manually (outside this pipeline, with DISM). Inspect the
   post-LCU `\Windows\Boot\EFI_EX\` directory for `bootmgfw_EX.efi`
   etc. If the EFI_EX directory is absent in the patched image,
   that is direct evidence that Server 2016 LCUs do not carry the
   PCA2023 staging assets, confirming Option C.
3. If the EFI_EX directory IS present after patching, switch to
   Option A: update `config-Server2016.json` to
   `EnableInstallWimUpdate=true` and add the recent LCU to the
   patch baseline, then re-run `PrepareBuildVerify` end to end.

**Phase 3 — Physical-hardware boot test**. If Option A or B
produces an output ISO that P12 classifies as `Health=Healthy`:

1. Write the ISO to USB and boot a physical machine whose firmware
   has revoked PCA2011 trust (post-CVE-2023-24932 mitigation or
   post-2026-06 PCA2011 expiry).
2. Confirm the machine progresses past the firmware's secure-boot
   verification and reaches Windows Setup.
3. Record the test in `docs/history/r07.0-physical-boot-test-report.md`
   with hardware model, firmware version, and a screenshot of the
   working setup screen.
