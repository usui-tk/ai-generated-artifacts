`\Windows\Boot\EFI\bootmgfw.efi` adjacent to it is PCA2011-signed.
The contents of `EFI_EX\` were not enumerated; the file inside

### Goal

Direct Authenticode chain inspection of
`EFI_EX\bootmgfw_ex.efi` and `EFI_EX\bootmgr_ex.efi` confirming
the chain contains "Windows UEFI CA 2023" (or whatever the actual
PCA2023-equivalent CN string is in the chain — Microsoft may have
shipped it under a different CN than the PCA-2011 one).

### Investigation plan

Reuse the r08.0 Step 5d mount procedure but enumerate
`EFI_EX\*.efi` and run the same `signtool /verify /pa /all` and
`Get-AuthenticodeSignature` chain walk against each.

### Pointers

---

- `install.wim` ships with `KB3211320` (2017-01-07) as the highest
  integrated LCU.
- The Make2023BootableMedia.ps1 prerequisite is **2024-4B**
  (`KB5036899`, 2024-04-09) or later.
- The Server 2016 profile defaults to `EnableInstallWimUpdate=false`,
  so P07 does not apply LCUs to install.wim before P10 inspects it.

P10 ConvertPca2023BootManager now skips cleanly via the
`Write-Warn`-and-marker path (Step 16) rather than the original
hard `throw`. From the dry-run perspective this is correct
behaviour, and P11 / P12 / P13 complete with a "Critical health"
verdict recorded in the final report.

**However**, an earlier Claude reply to the user contained this
acknowledgement (slightly paraphrased for documentation purposes):

> 完走後、`-Execute` で本番 ISO 生成 → でも Server 2016 EVAL は
> 前提条件未満なので PCA2023 変換は skip される(これは正しい挙動)。
> 本番動作確認は Server 2019/2022/2025 や、後日 LCU 適用済み媒体で

The user has correctly identified that this answer **invalidates the
operational use case the pipeline was built for**. The pipeline's
purpose includes producing PCA2023-bootable Server 2016 media so
that physical hardware (with PCA2011-revoked firmware) can boot
Server 2016 for test environments. If Server 2016 EVAL is
permanently locked out of PCA2023 conversion by its source media
vintage, then the EVAL ISO has no use as a starting point for
that operational goal.

This is the **highest-priority open issue** in the r07.0 cycle's
backlog. The PrepareBuildVerify dry-run completion milestone is
real but it does not, by itself, mean the pipeline produces
deployable output.

### Goal

Determine the **correct** workflow for producing a PCA2023-capable
Server 2016 ISO suitable for physical-hardware deployment, and
update the pipeline + documentation to support that workflow end
to end. The deliverable is one of:

- **Option A** — A profile change that enables
  `EnableInstallWimUpdate=true` for Server 2016, plus the
  patch-baseline updates (one or more LCUs leading up to 2024-4B
  or later) needed to lift the install.wim above the prereq, plus
  a verified end-to-end `-Execute All` run that produces an output
  ISO with `Health = Healthy` per P12.
- **Option B** — A documented workflow that uses a more recent
  Server 2016 ISO (e.g. a customer-supplied retail or volume-license
  media that already integrates a recent LCU) as the source, with
  the EVAL ISO documented as not viable for the PCA2023 use case.
- **Option C** — A documented finding that PCA2023 conversion is
  **not technically possible** on Server 2016 regardless of LCU
  level (e.g. because Server 2016 servicing is past the 2024-4B
  point at which Microsoft ships the EFI_EX staging assets), with
  evidence that closes the question.

### Investigation plan

**Phase 1 — Microsoft authoritative source**. Read the official
documentation for the
`Make2023BootableMedia.ps1` script and the
[microsoft/secureboot_objects](https://github.com/microsoft/secureboot_objects)
repository (the v1.4 / 2026-03-13 source the in-tree
`Convert-WimBootToPca2023Signed` was modelled after). Specifically:

1. What is the minimum supported source-media level for Server 2016?
2. Does the 2024-4B prerequisite apply to Server 2016 at all, or
   is it Windows 11 / Server 2022+ specific?
3. Does the EFI_EX staging directory ship with Server 2016 LCUs at
   any servicing date? Server 2016 is in Extended Security Updates
   (ESU) territory; ESU coverage and PCA2023 servicing may not
   overlap.

The likely answer is: **Server 2016 is not covered by the PCA2023
boot-manager refresh programme**. Server 2016 reaches end of
extended support on 2027-01-12 and is currently in ESU. The 2023
certificate refresh shipped via Windows 11 22H2/23H2 and Windows
Server 2025 servicing branches; backporting to Server 2016 was not
announced. If that is confirmed, the conclusion is Option C and the
pipeline needs to either (a) refuse `-EnablePca2023BootManager` for
Server 2016 with a clear error message, or (b) document the
limitation prominently in README so the operator does not waste
time on it.

**Phase 2 — Empirical check on Server 2016 LCU vintage**. If
Phase 1 leaves the question open:

1. Identify the most recent Server 2016 LCU available via Microsoft
   Update Catalog. As of 2026-05 this should be the 2026-05B LCU
   (the cycle the script currently targets).
2. Mount a fresh Server 2016 EVAL `install.wim` and apply that LCU
   manually (outside this pipeline, with DISM). Inspect the
   post-LCU `\Windows\Boot\EFI_EX\` directory for `bootmgfw_EX.efi`
   etc. If the EFI_EX directory is absent in the patched image,
   that is direct evidence that Server 2016 LCUs do not carry the
   PCA2023 staging assets, confirming Option C.
3. If the EFI_EX directory IS present after patching, switch to
   Option A: update `config-Server2016.json` to
   `EnableInstallWimUpdate=true` and add the recent LCU to the
   patch baseline, then re-run `PrepareBuildVerify` end to end.

**Phase 3 — Physical-hardware boot test**. If Option A or B
produces an output ISO that P12 classifies as `Health=Healthy`:

1. Write the ISO to USB and boot a physical machine whose firmware
   has revoked PCA2011 trust (post-CVE-2023-24932 mitigation or
   post-2026-06 PCA2011 expiry).
2. Confirm the machine progresses past the firmware's secure-boot
   verification and reaches Windows Setup.
3. Record the test in `docs/history/r07.0-physical-boot-test-report.md`
   with hardware model, firmware version, and a screenshot of the
   working setup screen.

### Context

The r07.0 cycle ran every step on Server 2016 ja-jp EVAL media only.
The pipeline supports Server 2019, 2022, and 2025 with the same
phase set, but no end-to-end verification has been done on any of
those OS families in the r07.0 timeframe.

Risks specific to each OS:

- **Server 2019**: shares the 2017-era servicing branch with
  Server 2016; the PCA2023 readiness question (P0 above) likely
  has the same answer.
- **Server 2022**: this is the **most interesting case** for the
  PCA2023 conversion path. Server 2022 servicing receives the
  2024-4B LCU, and the install.wim of a freshly-patched ISO should
  contain the EFI_EX staging directory. Server 2022 is therefore
  the realistic candidate for `-Execute` to actually trigger
  P10's conversion code, instead of skipping it.
- **Server 2025**: the existing P10 gate already routes
  Server 2025 to "skipped: firmware already includes 2023 certs",
  but the gate has not been exercised end to end. Confirm the
  skip path produces a clean P11-P13.

### Goal

A clean `PrepareBuildVerify` dry-run on each of Server 2019, 2022,
and 2025 (each in both en-us and ja-jp where the profile supports
both), with output captured to `docs/history/r07.0-os-coverage-matrix.md`.

For Server 2022, additionally a successful `-Execute Build` run
that triggers the **internal** `Convert-WimBootToPca2023Signed`
code path. This is the first time that code exercises in a real
end-to-end flow; expect at least one new latent-bug Step.

### Investigation plan

1. For each OS family, pull the cached EVAL ISO from the user's
   D:\ drive (paths are documented in the user's run logs).
2. Use the existing CLI invocation, swapping `-OsVersion` and
   `-WorkRoot` only:
   ```powershell
   .\Update-WindowsServerIso.ps1 -Action PrepareBuildVerify `
       -OsVersion Server2022 -OsLanguage ja-jp `
       -EvalIsoMode -UseBaselineOnly -EnablePca2023BootManager `
       -AutoInstallAdk -WorkRoot 'D:\UpdateWsi_2022'
   ```
3. Capture the full output, attach to the report, note any new
   defects that surface.
4. For Server 2022, switch to `-Action Build -Execute` once the
   dry-run passes, observe P10 conversion behaviour.

### Pointers

## P2 — Mojibake DISM-cache investigation

### Context

During the r07.0 Step 16 verification, install.wim idx 2's Japanese
edition name rendered with each character doubled
(`デデススククトトッッププ エエククススペペリリエエンンスス`). When the
operator switched WorkRoot from `D:\UpdateWsi` to
`D:\UpdateWsi_2016` between Steps 16 and 17, the mojibake stopped
reproducing despite an otherwise identical environment (same PS
host, same culture, same source ISO).

Working hypothesis: DISM mount-cache state from earlier aborted P10
runs in the `D:\UpdateWsi\` tree was poisoning subsequent
Get-WindowsImage enumerations. The fresh `D:\UpdateWsi_2016\` tree
side-stepped the cache. The investigation has been deferred
multiple times in favour of progressing the pipeline; with dry-run
completion now achieved, this can be picked up.

### Goal

Definitive root cause of the mojibake, plus either a fix or a
documented workaround. The current operator workaround ("use a
fresh WorkRoot per OS family") works but should be either
formalised in documentation or replaced with a real fix.

### Investigation plan

See the existing detailed plan in
`docs/history/mojibake-investigation-note.md`. The "Updated
investigation plan" section at the bottom of that file proposes
five concrete next steps.

### Pointers

- `docs/history/mojibake-investigation-note.md` — the long-form
  investigation note already in tree.
- `Update-WindowsServerIso.ps1` `Invoke-BuildPhase05_ExpandIso`
  where the affected `Write-Step` calls live.
