### 0.2 重要な発見・修正

**(1) `Argument types do not match` の根本原因解明**

r08.0 Step 2 セッションで実装を試みたが解決できなかった `System.ArgumentException: Argument types do not match` エラーの根本原因を、最小再現で特定しました:

```powershell
$list = New-Object System.Collections.Generic.List[object]
$list.Add([pscustomobject]@{Label='test1'}) | Out-Null
$list.Add([pscustomobject]@{Label='test2'}) | Out-Null

@($list)              # FAILS: Argument types do not match
[object[]]@($list)    # FAILS: Argument types do not match
$list.ToArray()       # OK
foreach ($x in $list) { $arr += $x }  # OK
```

`@(...)` 配列サブエクスプレッション演算子は、`System.Collections.Generic.List[object]` の要素が `pscustomobject` の場合に PowerShell 7.4.x の型変換ロジックで失敗します。一方、`List[string]` を `@()` でラップするケース(既存の `Test-Pca2023AuthenticodeChain` 等)では問題が出ません。

**回避策**: 関数出口で `$list.ToArray()` を使用する。これは新規 `Test-OutputIsoPca2023Readiness` 内で唯一の "違い" であり、Get-IsoBootCertReadiness パターンを忠実に踏襲する原則と矛盾しません(既存パターンの "Reasons" は `List[string]` であり `@()` で問題なく動作するため)。

**(2) Step 2 の方針が正しかったことを確認**

Step 2 の「Microsoft 公式 5-target」設計を忠実に実装した結果、5 つすべての target に Status 判定が割り当てられ、aggregate logic も `Fail > Warning > PassWithNotes > Pass` の優先順位で意図通り動作することを確認しました。

**(3) SCOPE clarifier の意義**

`Reasons[]` 配列に必ず付与する SCOPE 文言:

> "SCOPE: file presence + signer-chain only. Actual boot behaviour on
> firmware with PCA2011 revoked from DBX is NOT verified here. Manual
> boot test on hardware or a Hyper-V Gen2 VM with a PCA2023 Secure
> Boot template is required before production deployment."

これにより、P13 FinalReport を読む operator は「`Health = Healthy` であっても実機ブート検証は未済」という事実を明確に把握できます。Microsoft 公式 `Make2023BootableMedia.ps1` v1.4 自体が署名検証を行わない設計(Step 2 finding §3.3 参照)であることを踏まえると、この SCOPE 明記は Microsoft 公式実装の上位互換的な品質改善として位置づけられます。

## 1. 実装の詳細

### 1.1 `Test-OutputIsoPca2023Readiness` 関数

**配置**: `Get-IsoBootCertReadiness` (L7894+) の直後、`Get-Pca2023ReadinessSnapshot` (L8105) の直前。

**入力**:
- `[Parameter(Mandatory)] [string]$ExtractedMediaPath`

**出力**: pscustomobject、フィールド:
- `Generated` (DateTime) — 実行時刻
- `Available` (bool) — 検査が走ったかどうか
- `ErrorMessage` (string) — Available=false 時の理由
- `ExtractedMediaPath` (string) — 入力パスの echo
- `OverallStatus` (string) — `Pass` / `PassWithNotes` / `Warning` / `Fail` / `Unknown`
- `TargetChecks` (object[]) — 5 つの target の per-check 結果
- `Reasons` (string[]) — 非 Pass 項目のサマリ + SCOPE clarifier

**TargetChecks 各要素のフィールド**:
- `Label`, `Path`, `ExpectedSignature`, `ActualSignature`
- `IsPca2023`, `IsPca2011` (bool)
- `Status` (string), `Notes` (string)

### 1.2 5 target の Status mapping

| # | パス(ISO root 相対) | Required | Expected | Status logic |
|---|---|:---:|---|---|
| 1 | `\efi\boot\bootx64.efi` (or `bootaa64.efi`) | 必須 | PCA2023 | PCA2023 → Pass、PCA2011 / unknown / missing → Fail |
| 2 | `\bootmgr.efi` | 任意 | PCA2011 (Microsoft design) | 何が出ても、または missing でも → PassWithNotes(L876-L884 引用) |
| 3 | `\efi\microsoft\boot\efisys_ex.bin` | 必須 | (binary) | 存在 → Pass、missing → Fail |
| 4 | `\efi\microsoft\boot\fonts\*.ttf` | 必須 | (fonts) | 存在 → Pass、missing/empty → Warning |
| 5 | `\EFI\Microsoft\Boot\boot.stl` | 任意 | (cert trust list) | 存在 → Pass、missing → PassWithNotes |

**ARM64 対応**: Target #1 は `bootx64.efi` が存在しない場合 `bootaa64.efi` をフォールバック検査します。

**OverallStatus 集約**: 優先順位 Fail > Warning > PassWithNotes > Pass。1 つでも Fail → Fail、なければ Warning があれば Warning、それもなければ PassWithNotes があれば PassWithNotes、すべて Pass なら Pass。

### 1.3 既存関数の拡張

#### `Get-Pca2023ReadinessSnapshot` (L8105+)

- 2 つの return 文(early-return on `-not $emb.Available`、および末尾の正常パス)の両方に `OutputCheck = $null` を追加。
- これにより、`$snapshot.OutputCheck` への代入が PSScriptAnalyzer / psa.py の "未宣言プロパティ" 警告(PSA2009)を起こさなくなります。

#### `Show-Pca2023ReadinessSnapshot` (L8217+)

- 新規パラメータ `$OutputCheck`(オプション、未指定時は描画スキップ)。
- Compact モード: 既存の 1 行サマリの後に、Output ISO check の 1 行を追加:
  ```
  Output ISO check : overall=Pass     targets=5 (Pass=3 PassWithNotes=1 Warn=0 Fail=0)
  ```
- 非 Compact モード: 既存の "SecureBoot servicing keys" ブロックの後に、"Output ISO PCA2023 readiness" ブロックを追加。5 target の per-target 詳細(Status / expected / actual / notes)を列挙。

#### `Format-Pca2023ReadinessForReport` (L8328+)

- 新規パラメータ `$OutputCheck`。
- text レポート末尾に "Output ISO PCA2023 readiness (post-conversion, file-based)" セクションを追加。P13 FinalReport および `pca2023_readiness.md` の両方で使用されます。

### 1.4 Phase 統合

#### P10 (`Invoke-BuildPhase10_ConvertPca2023BootManager`、L10670+)

ISO 再アセンブリ後の post-flight snapshot 直後に挿入:

```powershell
# 既存: post-flight snapshot
$post = Get-OrEnsurePca2023Snapshot ... -Force
Show-Pca2023ReadinessSnapshot ... -Compact   # 既存

# 新規: Output ISO 5-target check
$outputCheck = Test-OutputIsoPca2023Readiness -ExtractedMediaPath $extractedPath
$post.OutputCheck = $outputCheck
Show-Pca2023ReadinessSnapshot -Snapshot $post -Compact -OutputCheck $outputCheck
```

P10 が走ったあとは `$Script:Pca2023Snapshot.OutputCheck` に Output check 結果が乗ります。

#### P12 (`Invoke-VerifyPhase12_VerifyPca2023Readiness`、L10880+)

P10 が走っているか否かに関わらず idempotent に動作するよう、`Get-OrEnsurePca2023Snapshot -Force` で snapshot を再構築した直後に Output check を実行:

```powershell
$snapshot = Get-OrEnsurePca2023Snapshot ... -Force
$outputCheck = Test-OutputIsoPca2023Readiness -ExtractedMediaPath $extractedPath
$snapshot.OutputCheck = $outputCheck   # psa-disable PSA2009
Show-Pca2023ReadinessSnapshot -Snapshot $snapshot -OutputCheck $outputCheck
```

Markdown レポート(`pca2023_readiness.md`)の "Detail" コードブロックの後に、新規セクション "Output ISO PCA2023 Readiness (post-conversion)" を追加。5 target を Markdown テーブル形式で列挙、続いて `Reasons` を bullet 列挙します。

JSON レポート(`pca2023_readiness.json`)は `$snapshot | ConvertTo-Json -Depth 10` の出力なので、`OutputCheck` フィールドが自動的にシリアライズされます。下流ツールから消費する場合は `.OutputCheck.OverallStatus` および `.OutputCheck.TargetChecks[*]` を参照できます。

#### P13 (`Invoke-ReportPhase13_FinalReport`、L11077+)

既存の `Show-Pca2023ReadinessSnapshot -Compact` 呼び出しに `-OutputCheck` を追加:

```powershell
$ocForReport = $null
if ($Script:Pca2023Snapshot.PSObject.Properties['OutputCheck']) {
    $ocForReport = $Script:Pca2023Snapshot.OutputCheck
}
Show-Pca2023ReadinessSnapshot -Snapshot $Script:Pca2023Snapshot -Compact -OutputCheck $ocForReport
```

`PSObject.Properties` で defensive check しているのは、P12 が skip された(extracted media なし)場合に snapshot が初期化されないシナリオへの保険です。

## 4. 設計判断のメモ

### 4.1 関数の責務境界(Get-IsoBootCertReadiness との対比)

| 項目 | `Get-IsoBootCertReadiness` | `Test-OutputIsoPca2023Readiness` |
|---|---|---|
| 入力 | extracted media path | extracted media path |
| 視点 | INPUT(P10 適用前)の boot.wim 内部状態 | OUTPUT(P10 適用後)の ISO root 直下のファイル |
| マウント | boot.wim を read-only mount | マウントなし(file-system Test-Path のみ) |
| Authenticode | bootx64.efi の primary signer chain | 5 target のうち 1 と 2 の signer chain |
| レジストリ参照 | install.wim の SYSTEM hive(SecureBoot servicing keys) | なし |
| 副作用 | DISM mount / reg load(transient) | 完全 read-only |

両関数は補完関係にあり、P12 で両方が走ることで「入力 ISO がどう、出力 ISO がどう」という双方向の readiness レポートが揃います。

### 4.2 なぜ `boot.stl` の missing は PassWithNotes か

Microsoft `Make2023BootableMedia.ps1` v1.4 L909-L911 が明示的にこう書いています:

```powershell
$bootStlSource = $bootWimMount + "\Windows\Boot\EFI\boot.stl"
if (-not (Test-Path -Path $bootStlSource)) {
    Write-Dbg-Host "[boot.stl] not found in mounted boot.wim. Skipping."
}
```

Microsoft 公式実装が "Skipping" を許容するロジックを持っている以上、ある OS / LCU level では boot.stl が存在しないこと自体が by-design です。本関数で Warning ではなく PassWithNotes にしたのはこのため。

### 4.3 なぜ Target #1 だけ「PCA2011 検出 = Fail」か

UEFI Secure Boot の "critical path" だからです。Firmware が最初に検証するのは `\efi\boot\bootx64.efi`(removable media boot fallback path)であり、ここが PCA2011 のままだと、PCA2011 が DBX で revoke された firmware では起動拒否されます。これは正に本パイプライン(P10)の存在理由そのものなので、PCA2011 のままの Output は「P10 の効果が出ていない」 = Fail と判定。

他の target は補助的役割なので missing は Warning / PassWithNotes に留めます。

### 4.4 内部 List 型の使い分け

| 用途 | 型 | 関数出口の変換 |
|---|---|---|
| `Reasons[]` (文字列の集合) | `List[string]` | `@($reasons)` でよい |
| `TargetChecks[]` (pscustomobject の集合) | `List[object]` | **`$checks.ToArray()` 必須**(`@($checks)` は `Argument types do not match` エラー) |
| `BootX64ChainTokens[]` (既存、文字列の集合) | `List[string]` | `@($tokens)` でよい(参考: `Test-Pca2023AuthenticodeChain` L7878) |

この使い分けは関数内コメントで明示しています。将来の保守者が新規 helper を追加する際の参照点として有効です。

## 6. Appendix

### 6.1 Argument types do not match の最小再現

検証時に使用した最小スクリプト(本セッション中、Linux pwsh 7.4.6 で確認):

```powershell
$list = New-Object System.Collections.Generic.List[object]
$list.Add([pscustomobject]@{Label='test1'; Status='Pass'}) | Out-Null
$list.Add([pscustomobject]@{Label='test2'; Status='Fail'}) | Out-Null

# FAILS with "Argument types do not match":
try { $arr = @($list); 'OK' } catch { 'FAIL: ' + $_.Exception.Message }

# FAILS with same error:
try { $arr = [object[]]@($list); 'OK' } catch { 'FAIL: ' + $_.Exception.Message }

# WORKS:
$arr = $list.ToArray()                # System.Object[], count=2
$arr = @(); foreach ($x in $list) { $arr += $x }  # System.Object[], count=2
```

参考: 同じ pattern を `List[string]` で実行した場合は `@(...)` が問題なく動作します。違いは「要素が pscustomobject かどうか」。
