## Phase 5 v1: expand.exe self-overwrite bug

### スクリプト
`wsusscn2-step5-package-xml-poc.ps1`

### 失敗内容

```
expand.exe -F:package.xml D:\Temp\poc\package.cab D:\Temp\poc
→ "Cannot expand a file onto itself: d:\temp\poc\package.cab"
```

### 原因

expand.exe の `-F:filter` フラグは、ソースと宛先が同じディレクトリで、宛先ディレクトリに同名ファイルが存在する場合に self-overwrite エラーを返す。kbupdate-library の `buildfromwsus.ps1` が `Microsoft.Deployment.Compression.Cab.dll` を使用して同じディレクトリで成功している理由は、`UnpackFile(name, destinationFullPath)` で **出力先パスを完全指定** しているため。

### 試した修正

Stage 分離 (Stage 1 / Stage 2 を別ディレクトリにする) を Phase 5 v2 で実装。

## r09.0 Step 1 スコープの最終確定

### 実装する (Master XML のみ、高速)

| 項目 | 取得方法 |
|---|---|
| KB ID | FileLocation URL から regex `kb(\d+)` |
| Prerequisites (簡易版) | Master XML の `<Prerequisites><UpdateId Id="GUID"/>` |
| SupersededBy | Master XML の `<SupersededBy><Revision Id="RevisionId"/>` |
| Bundle/Standalone 識別 | `@IsBundle`, `@DeploymentAction` |
| BundledBy | `<BundledBy><Revision Id="..."/>` |
| Categories (raw GUID) | `<Category Type="..." Id="..."/>` |

### r10.x 以降に保留

| 項目 | 理由 |
|---|---|
| SupersededUpdates (順方向) | 個別 cab 必要、2.5h かかる、0x800f0823 問題には不要 |
| Prerequisites 詳細版 (`<AtLeastOne>`) | 同上 |
| ApplicabilityRules | 同上 |
| Category Type → OS family 名 mapping | 個別 cab 必要、現時点は raw GUID で保存 |
| KB ID element-level (Metadata) | 個別 cab、Master XML の URL ベースで十分 |

### 根拠

- 0x800f0823 問題の本質: KB5087537 LCU → KB5088064 SSU の事前依存
- 必要なデータ: Prerequisites + (オプション) SupersededBy
- 両方とも Master XML だけで取得可能

## 設計判断の蓄積

### D1: CAB 展開方式 (Phase 5 v3 で確定)

**7-Zip を主軸に採用**

理由:
1. expand.exe バグが Phase 5 v2 で実証された (Windows 11 build 26100)
2. Microsoft OS ツール (expand.exe / Shell.Application) は将来同様の挙動変更リスク
3. 7-Zip は長期メンテされた OSS (2000 年〜)、公式配布元から controlled に取得可能
4. `Deploy-AMDChipsetDriverOnWindowsServer.ps1` で既に確立済みのパターン

実装パターン (Deploy-AMD から 1:1 移植):
- `Get-SevenZipPath` (Program Files / PATH を探索)
- `Get-LatestSevenZipUrl` (3-tier fallback: 7-zip.org HTML / GitHub API / pinned URL)
- `Install-SevenZipFallback` (winget → MSI 直接)
- コマンド: `& $sevenZip x $archive ('-o' + $dest) -y -bsp0 -bso0`
- 終了コード解釈: 0=ok, 1=warn, >=2=fatal

### D2: parser データソース (Phase 5 v4 で確定)

**Master XML のみ使用 (r09.0 では)**

理由:
1. 0x800f0823 問題に必要な情報 (Prerequisites + SupersededBy) は Master XML だけで取得可能
2. 個別 cab 解析は 2.5 時間 / 15-20 GB かかり実用性に欠ける
3. r09.0 のスコープは「ベースライン整合性検証」、詳細な依存グラフは不要

### D3: parser ストリーミング方式 (Phase 5 v3 で確定)

**XmlReader streaming を採用**

理由:
1. Phase 5 v3 で XmlDocument DOM 読み込みは peak +536 MB を確認
2. parser は CI/CD 環境でも実行されるため、メモリ効率重視
3. XmlReader なら peak 50 MB 程度に抑制可能

## 反省点と学び

### L1: サンプルサイズの問題 (Phase 5 v3 → v4 で顕在化)

**問題**: Updates[0] と Updates[100] の 2 サンプルだけで「Master XML に Supersedes 情報は無い」と結論した。

**修正**: Phase 5 v4 の全文字列検索で 14,059 件の `<SupersededBy>` を発見。これは Update 全体の 10.3% という大きな割合であり、2 サンプルでは偶然見つからない確率が十分に高い。

**学び**: 136,102 件の Updates を持つ XML に対して 2 サンプルは絶望的に少ない。網羅的な文字列検索で全体傾向を把握してから、サンプル要素を選ぶべき。

### L2: 設計哲学の認識遅れ (Phase 5 v1 → v3)

**問題**: 「Microsoft OS ツール (expand.exe, Shell.Application) は標準で安全」という思い込みがあった。

**修正**: Phase 5 v1-v2 で expand.exe バグが実証され、Takayuki さんの「Microsoft OS ツールに依存しすぎると将来動かなくなる」哲学を反映し、Phase 5 v3 で 7-Zip 採用に切り替えた。

**学び**: Microsoft OS ツールの仕様変更/挙動変更は実際に起きる。Phase 5 v2 で expand.exe `-F:` フラグが Windows 11 build 26100 で壊れていたのは、まさにこの哲学の正当性を実証する結果となった。3rd party の長期メンテ OSS (7-Zip 等) のほうが、Microsoft OS ツールよりも長期的に安定。

### L3: 段階的調査の重要性

Phase 5 を 4 セッションに分けたことで、各段階での仮説検証が可能になった:

| Phase | 仮説 | 結果 |
|---|---|---|
| v1 | expand.exe で動くか? | No (バグ確認) |
| v2 | Stage 分離で動くか? | Yes だが Microsoft OS 依存の問題が残る |
| v3 | 7-Zip で動くか + Master XML 構造は? | Yes、構造把握 |
| v4 | Supersedes はどこ? | 二重ソース構造を発見 |

各段階で得られた知見を次の段階に活かすパターンが奏功した。一度に全てを実装しようとせず、PoC で段階的に検証する設計が r09.0 の規模では必須。
